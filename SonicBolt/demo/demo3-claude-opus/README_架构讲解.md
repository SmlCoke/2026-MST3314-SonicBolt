# Conv1 架构讲解

> 本文档详细介绍 SonicBolt Conv1 模块的硬件微架构设计，
> 包括整体架构、流水线设计、存储策略、性能分析等。

---

## 一、设计目标与约束

| 指标 | 目标值 | 备注 |
|------|--------|------|
| 吞吐量 | ≥ 1000K FPS | 高性能应用场景 |
| 工艺 | 0.18um | 课程指定 |
| 时钟频率 | 100~120 MHz | 老师建议 |
| 输入 | (1, 30, 10) INT8 | 每帧 300 字节 |
| 输出 | (32, 20, 4) INT8 | 每帧 2560 字节 |
| 卷积核 | (32, 1, 11, 7) INT8 | stride=1, pad=0 |

**性能估算**：@100MHz，每帧需在 100 周期内完成 → 实际设计 ~116 周期/帧 → @120MHz 约 1034K FPS ✓

## 三、核心设计决策

### 3.1 为什么选择 32 通道全并行？

卷积核有 32 个输出通道。如果分时复用（如每次只算 1 个通道），需要重复 32 次窗口数据读取，输入带宽利用率仅 1/32。

**32 通道全并行方案**:
- **1 次窗口读取 → 32 个 MAC 树同时计算** → 100% 带宽利用率
- 代价：32 × 77 = 2464 个 INT8 乘法器
- 收益：1 个输出空间位置/周期

### 3.2 为什么选择环形行缓冲（而非移位寄存器）？

| 方案 | 每次push翻转的DFF | 组合逻辑面积 | 适用场景 |
|------|-------------------|-------------|---------|
| A: 移位寄存器 | 11×80 = 880 个 | 较小（直连） | 小核（如3×3） |
| **B: 环形缓冲** | **1×80 = 80 个** | **较大（11:1 MUX×77）** | **大核（如11×7）** |

对于 11 行的大卷积核，环形缓冲**节省约 90% 的动态功耗**。虽然 MUX 面积增加，但在 0.18um 工艺下 MUX 面积远小于 DFF 翻转带来的功耗开销。

### 3.3 权重存储策略

```
外部 SRAM ──(逐通道读取)──→ 片上寄存器文件
                              ↓
                        32路并行读取
```

- **预加载阶段**（32 周期）：从外部 SRAM 逐通道读取权重和偏置，存入片上寄存器
- **计算阶段**：32 个 MAC 树同时从各自的寄存器读取权重（并行无冲突）
- **优势**：避免计算时的 SRAM 读写冲突，实现 1 像素/周期吞吐

## 四、流水线设计详解

### 4.1 数据通路流水线（5 级）

```
Stage    │  模块                │ 位宽变化          │ 延迟
─────────┼──────────────────────┼───────────────────┼──────
  (comb) │ Window Extract       │ 880b → 616b       │ 0 拍
  S1     │ MAC77_Mult           │ 2×616b → 1232b    │ 1 拍
  S2     │ MAC77_AddTree_s1     │ 1232b → 200b      │ 1 拍
  S3     │ MAC77_AddTree_s2     │ 200b+32b → 32b    │ 1 拍
  S4     │ requant_relu (乘法)  │ 32b → 48b         │ 1 拍
  S5     │ requant_relu (移位)  │ 48b → 8b          │ 1 拍
─────────┼──────────────────────┼───────────────────┼──────
  总计   │                      │ INT8 → INT8       │ 5 拍
```

### 4.2 流水线时序图

以连续 4 个输出位置为例（同一行的 col=0,1,2,3）：

```
Cycle:     1     2     3     4     5     6     7     8
           ┃     ┃     ┃     ┃     ┃     ┃     ┃     ┃
WinExtr:  [W0]  [W1]  [W2]  [W3]
MAC_S1:         [W0]  [W1]  [W2]  [W3]
MAC_S2:               [W0]  [W1]  [W2]  [W3]
MAC_S3:                     [W0]  [W1]  [W2]  [W3]
RQ_S4:                            [W0]  [W1]  [W2]  [W3]
RQ_S5:                                  [W0]  [W1]  [W2] [W3]
out_valid:                                ✓     ✓     ✓    ✓
```

- 首个输出在第 6 个周期出现（5 拍延迟）
- **之后每周期输出 1 个空间位置的 32 通道数据**（全流水无气泡）

### 4.3 行切换时序

当 `col_cnt` 从 3 回到 0（需要新行数据）：

```
Cycle:    N    N+1   N+2   N+3   N+4   N+5
          ┃     ┃     ┃     ┃     ┃     ┃
col_cnt:  3     -     0     1     2     3
MAC:     [W3]  wait  [W0'] [W1'] [W2'] [W3']
Row:     ────  req   ──push──────────────────
SRAM:          addr  data
               →     ←
状态:    CALC  等待行  CALC  CALC  CALC  CALC
```

- **N+1 周期**：发送新行地址到 SRAM，`wait_row=1`
- **N+2 周期**：SRAM 返回数据（1 拍延迟），push 到行缓冲，恢复计算
- **代价**：每行切换增加 **1 个气泡周期**
- **总周期**：80 (计算) + 19 (行切换气泡) = **99 周期**

### 4.4 偏置对齐

`bias` 在 Stage 3 才需要，但在 Stage 1 输入时就已确定。因此需要延迟 2 拍：

```verilog
// 在 MAC_Tree_77 内部
bias_d1 <= bias_in;    // 延迟 1 拍
bias_d2 <= bias_d1;    // 延迟 2 拍，对齐 MAC77_AddTree_s2 的输入
```

## 五、FSM 状态机详解

### 5.1 状态转移图

```
                ┌─────────┐
                │ S_IDLE  │◄─────────────────────┐
                └────┬────┘                      │
                     │ start=1                   │
                     ▼                           │
           ┌─────────────────┐                   │
           │ S_LOAD_PARAM    │ 32 周期            │
           │ 加载权重+偏置   │                    │
           └────────┬────────┘                   │
                    │ load_cnt==31               │
                    ▼                            │
           ┌─────────────────┐                   │
           │ S_FILL_LB       │ 11 周期            │
           │ 填充行缓冲前11行 │                    │
           └────────┬────────┘                   │
                    │ fill_cnt==10               │
                    ▼                            │
           ┌─────────────────┐                   │
           │ S_CALC          │ ~99 周期           │
           │ 核心卷积计算     │                    │
           │ row×col遍历     │                    │
           └────────┬────────┘                   │
                    │ row=19, col=3              │
                    ▼                            │
           ┌─────────────────┐                   │
           │ S_DRAIN         │ 5 周期             │
           │ 流水线排空       │                    │
           └────────┬────────┘                   │
                    │ drain_cnt==4              │
                    ▼                            │
           ┌─────────────────┐                   │
           │ S_DONE          │ 1 周期             │
           │ done=1          ├───────────────────┘
           └─────────────────┘
```

### 5.2 各状态详解

| 状态 | 周期数 | 动作 |
|------|--------|------|
| **S_IDLE** | - | 等待 `start` 脉冲 |
| **S_LOAD_PARAM** | 32 | 每周期读 1 通道的权重(616b)+偏置(32b)，存入寄存器文件 |
| **S_FILL_LB** | 11 | 读输入行 0~10 推入行缓冲，每行 80-bit |
| **S_CALC** | ~99 | 遍历 20×4=80 个输出位置。同行内无气泡，行切换有 1 周期延迟 |
| **S_DRAIN** | 5 | 等待最后的数据通过 5 级流水线 |
| **S_DONE** | 1 | 拉高 `done` 信号，返回 IDLE |

**总周期数**: 32 + 11 + 99 + 5 + 1 = **148 周期**（首帧，含参数加载）
**连续帧**: 11 + 99 + 5 + 1 = **116 周期**（权重已加载，跳过 LOAD_PARAM）

## 六、片上存储策略

### 6.1 存储需求分析

| 数据 | 大小 | 存储方式 | 理由 |
|------|------|----------|------|
| 输入特征图 | 300 B | 外部 SRAM，逐行读取 | 行缓冲仅存 11 行，节省面积 |
| 权重 | 2464 B | 片上寄存器文件 | 32 通道并行读取，SRAM 无法提供 |
| 偏置 | 128 B | 片上寄存器文件 | 同上 |
| 输出 | 2560 B | 直接输出（或下级缓存） | 流式输出，不存储 |

### 6.2 为什么权重用寄存器而不用 SRAM？

SRAM 是**单端口**的（老师提到），每周期只能读 1 个地址。但我们需要 **32 个通道同时读取各自的权重**。

解决方案对比:

| 方案 | 可行性 | 代价 |
|------|--------|------|
| 32 块独立 SRAM | ✓ | 面积很大（分布式 SRAM） |
| 1 块 SRAM + 分时复用 | ✓ | 吞吐量降为 1/32 |
| **预加载到寄存器** | **✓** | **一次性 32 周期开销** |

我们选择"预加载到寄存器"：用 32 周期从 SRAM 逐通道读取，之后计算阶段零开销并行读。

### 6.3 行缓冲的 SRAM vs 寄存器选择

行缓冲只有 11 × 80-bit = 110 Bytes，用寄存器实现：
- 面积可控（<1K 门）
- 读取零延迟
- 允许同时读 11 行 + 写 1 行

如果更大规模（如卷积核高度 > 30），应改用双端口 SRAM。

## 七、位宽链分析

追踪数据从输入到输出的位宽变化：

```
输入激活:  INT8   (8-bit)    范围: [-128, 127]
权重:      INT8   (8-bit)    范围: [-128, 127]
                    │
          ──── 乘法 ────
                    │
乘积:      INT16  (16-bit)   范围: [-16384, 16129]
                    │
      ──── 8 元素求和 ────
                    │
部分和:    INT20  (20-bit)   最大: 8 × 16384 = 131072 < 2^20
                    │
      ──── 10 组求和 ────
                    │
总和:      INT24  (24-bit)   最大: 10 × 131072 < 2^24
                    │
      ──── 加偏置 ────
                    │
MAC结果:   INT32  (32-bit)   偏置范围很大，保守用 32 位
                    │
      ──── ×111 ────
                    │
乘法结果:  INT48  (48-bit)   INT32 × INT16 → INT48
                    │
      ──── >>>14 ────
                    │
移位后:    INT34  (有效位)   但仍用 48 位线宽
                    │
      ──── ReLU + 饱和 ────
                    │
输出:      INT8   (8-bit)    范围: [0, 127]（ReLU后无负值）
```

## 八、重量化（Requantization）详解

### 8.1 为什么需要重量化？

卷积的中间结果是 INT32（32位），但下一层的输入必须是 INT8（8位）。直接截断会丢失大量信息，需要一个"聪明的缩放"。

### 8.2 数学公式

$$O_{INT8} = \text{clamp}\left(\left\lfloor \frac{I_{INT32} \times M_0}{2^n} \right\rfloor, 0, 127\right)$$

Conv1 层参数: $M_0 = 111$, $n = 14$

等价于: $O = \text{ReLU}\left(\text{round}\left(I \times \frac{111}{16384}\right)\right) = \text{ReLU}\left(\text{round}(I \times 0.00677)\right)$

### 8.3 硬件实现

```
┌──────────┐    ┌───────────┐    ┌────────────────┐
│  INT32   │───→│  × M0     │───→│  >>> N         │───→ INT8
│ MAC结果  │    │  (乘法器) │    │  (连线，0面积) │
│          │    │  → INT48  │    │  + ReLU + 饱和 │
└──────────┘    └───────────┘    └────────────────┘
   流水线 S4        1 拍              流水线 S5  1 拍
```

`>>> N` 是算术右移，综合器会实现为简单的连线重排（零面积零延迟），所以实际面积只有乘法器的开销。

### 8.4 饱和截断规则

```python
if shifted < 0:       out = 0      # ReLU
elif shifted > 127:   out = 127    # 正向饱和
else:                 out = shifted # 正常
```

## 九、Input Broadcasting 架构

这是本设计最核心的性能优化：**同一个窗口数据广播到 32 棵 MAC 树**。

```
                    ┌──────────────┐
                    │ Window Data  │
                    │  616-bit     │
                    └──────┬───────┘
                           │ 广播（fan-out = 32）
          ┌────────┬───────┼───────┬────────┐
          ▼        ▼       ▼       ▼        ▼
     ┌────────┐┌────────┐┌────────┐    ┌────────┐
     │MAC ch0 ││MAC ch1 ││MAC ch2 │... │MAC ch31│
     │wgt[0]  ││wgt[1]  ││wgt[2]  │    │wgt[31] │
     │bias[0] ││bias[1] ││bias[2] │    │bias[31]│
     └───┬────┘└───┬────┘└───┬────┘    └───┬────┘
         │         │         │              │
    INT32[0]  INT32[1]  INT32[2]  ...  INT32[31]
```

- **数据复用率**: 1 次窗口提取 → 32 次使用
- **理论乘法利用率**: 100%（每个 MAC 每周期都在工作）
- **总乘法器数**: 32 × 77 = 2464 个 INT8×INT8 乘法器

## 十、性能分析

### 10.1 延迟分析 (Latency)

| 阶段 | 周期数 | 备注 |
|------|--------|------|
| 参数加载 | 32 | 首帧需要，后续帧可跳过 |
| 行填充 | 11 | 读入前 11 行 |
| 核心计算 | 80 + 19 = 99 | 80 个输出位置 + 19 次行切换 |
| 流水线排空 | 5 | 5 级流水线延迟 |
| **总计（首帧）** | **148** | 包含参数加载 |
| **总计（连续帧）** | **116** | 跳过参数加载 |

### 10.2 吞吐量分析 (Throughput)

$$\text{FPS} = \frac{f_{clk}}{\text{Cycles/Frame}} = \frac{100\text{MHz}}{116} \approx 862\text{K FPS}$$

@120MHz:

$$\text{FPS} = \frac{120\text{MHz}}{116} \approx 1034\text{K FPS} > 1000\text{K}$$

### 10.3 资源估算

| 组件 | 数量 | 面积估算 |
|------|------|----------|
| INT8×INT8 乘法器 | 2464 | 主要面积贡献 |
| INT16 加法器（S2） | 320 | 分组求和 |
| INT20 加法器（S3） | 32×10 | 最终求和 |
| INT32×INT16 乘法器 | 32 | 重量化 |
| 行缓冲寄存器 | 11×80 bit | 880 bit |
| 权重寄存器 | 32×616 bit | 19712 bit |
| 偏置寄存器 | 32×32 bit | 1024 bit |

## 十一、数据流完整示例

以计算输出位置 `(row_out=0, col_out=0)` 为例：

```
1. 行缓冲中有第 0~10 行数据
2. col_cnt=0，窗口提取：
   从每行取第 0~6 列（7 个 INT8）
   → 77 个 INT8 展平为 616-bit

3. 广播到 32 个 MAC 树：
   MAC[ch]: win × weight_reg[ch] + bias_reg[ch]
   经过 3 拍得到 32 个 INT32 结果

4. 重量化 + ReLU（2 拍）:
   out[ch] = clamp(max(MAC[ch] × 111 >>> 14, 0), 127)

5. 输出：out_valid=1, out_data={ch31_byte, ..., ch0_byte}
   对应 golden[0] = Out_Conv.txt 中所有通道在 (row=0, col=0) 的值
```

## 十二、与 MiniCNN 参考实现的对比

| 设计点 | MiniCNN | SonicBolt Conv1 |
|--------|---------|-----------------|
| 行缓冲 | 隐式（内存偏移） | 显式环形缓冲 |
| MAC 分组 | 4组×11单元×7乘法 | 32通道×77路乘法树 |
| 通道并行度 | 分时复用（32周期/像素） | **全并行（1周期/像素）** |
| 权重存储 | 8块 SRAM | 片上寄存器预加载 |
| 流水线级数 | ~7级 | **5级** |
| 重量化参数 | M0=111, N=14 | M0=111, N=14（相同） |
| 遍历方式 | cnt/pos 两级计数 | row_cnt/col_cnt |
| 吞吐量 | ~3K FPS | **~860K FPS** |
