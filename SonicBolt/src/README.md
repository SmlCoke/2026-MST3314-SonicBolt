## I. 系统总体架构总览

SonicBolt 是一个高度定制化、以流式执行为主的、面向语音检测的 CNN 硬件加速器。整个系统期望在 $.18um$ 工艺、 $100\sim120 MHz$ 极高的帧率计算目标（如 1000k FPS 的计算指标）。

整个顶层架构分为四个核心子系统级阶段：

### 1.1 Conv 子系统

1. **功能定位：承接输入图像的首层标准卷积网络（Standard Convolution）**
2. **输入尺寸**： $1 \times 30 \times 10$（通道 $\times$ 高 $\times$ 宽）。
3. **卷积核尺寸**：32 个 $1 \times 11 \times 7$ 卷积核。
4. **核心任务**：提取图像初级大尺度特征。其自带片上 SRAM 作为全图缓存。将原图切片发送为 **流式 Token**（以 `pos` 和 `group` 搭建二维发射坐标），向后提供 $32 \times 20 \times 4$ 特征图的 `Tile` 串、每个 `Tile` 尺寸 $4 \times 4\times 4$ 
5. 详细设计细节参考 `/SonicBolt/src/conv/` 下的 RTL 模块以及 [README文档](/SonicBolt/src/conv/docs/README.md)。


### 1.2 DWConv 子系统

1. **功能定位**：深度可分离卷积（Depthwise Convolution）。
2. **输入尺寸**:  $4 \times 4 \times 4$  `tile`
3. **卷积核尺寸**: $32 \times 1 \times 3 \times 3$ 。
4. **核心任务**：按通道空间执行精细化特征提取。直接透传接收 Conv 的每 $4\times 2\times 2$ 空间 Token 进行 $\times 3$ 行乘与加处理，输出尺寸规约为 $32 \times 18 \times 2$，每个 `tile` 尺寸 $4 \times 2 \times 2$。
5. 详细设计细节参考 `/SonicBolt/src/dwconv/` 下的 RTL 模块以及 [README文档](/SonicBolt/src/dwconv/docs/README.md)。

### 1.3 PWConv 子系统
1. **逐点卷积（Pointwise Convolution）**。
2. **输入尺寸**: $4 \times 2 \times 2$
3. **卷积核尺寸**:  $32 \times 32 \times 1 \times 1$ 。
4. **核心任务**：跨层整合特征通道。这层为了实现 $32\text{ch}$ 的全通道累和操作，巧妙地在入口处利用 **双缓冲（Ping-Pong Buffer）** 结构，暂存相同 `pos` 下的所有通道输入组并统一乘加，输出尺寸维持 $32 \times 18 \times 2$，每个 `tile` 尺寸 $4 \times 2 \times 2$。
5. 详细设计细节参考 `./SonicBolt/src/pwconv/` 下的 RTL 模块以及 [README文档](/SonicBolt/src/pwconv/docs/README.md)。

### 1.4 Post Process 后处理子系统
1. **功能定位**：最大池化、展平、全连接、Sigmoid。
2. **核心任务**：首先将数据流进行对应的 **2x2 MaxPool** 的极大值收纳运算进而降维至 $32 \times 9 \times 1$ 即 **288 维的一维长向量**（这就是 **pos-group** 架构的核心来源，以 1 token(4 channel)/cycle 为核心指标构建的二维坐标架构）。接着通过流水线传送级 **FC** 累加层计算各个类别（Class 0, Class 1）的分数矩阵得分，最后经过内建量化与硬件 LUT 查表（**Sigmoid** 替代层）输出分类结果。
3. 详细设计细节参考 `/SonicBolt/src/post_process/` 下的 RTL 模块以及 [README文档](/SonicBolt/src/post_process/docs/README.md)。

## II. 数据流与调度核心

本系统最大的亮点在于抛弃了传统的“层间等待”结构，将全局抽象为一套共同遵守的“流协议”。
各层之间严格保持“无等待”的计算衔接，数据以 token/`tile` 为最小计算单元，借助包含 pos-group 在内的五大元数据定位，实现高吞吐、无停顿的流水线计算。

### 2.1 调度核心: pos-group 架构

MaxPool 层的输出是一个 $9\times 32$ 的二维张量，它有 $32$ 个通道，每个通道有 $9$ 个空间位置，我们把**这样的空间位置称为 `pos`**，其取值范围是 $0\sim 8$。为了实现最终 $1000k\text{FPS}$ 的性能指标，我们需要在 $100 MHz$ 的时钟频率下，使得**流水线满载**时，平均**每 $N$ 个周期**就能输出一张图的结果，这里 $N < 100$ 。或者说平均处理一张图的有效吞吐（即**连续两张图完成计算的时间间隔**）不得超过100个时钟周期。

因此，我们设计了如下架构，在**流水线满载**时，每次都能处理这 $9\times 32$ 个数值中的 4 个，这样就能在**流水线满载**的情况下实现每 $288/4 = 72$ 个周期输出一张图的结果。其中的这 4 个数据，就是**同一个 pos 下的 4 个通道的数据**，我们把**这 4 个通道的组合称为一个 `group`**。因此每个 pos 下有 8 个 group（32 个通道 / 4 个通道每组 = 8 组），也就是说其取值范围是 $0\sim 7$ 。

因此，我们就可以用二维坐标 $(\text{pos}, \text{group})$ 来描述每个周期输出的这 4 个通道数据的空间位置，例如 $(0, 0)$ 就是表示第 $0$ 个位置下通道 $0\sim 3$ 的数据， $(0, 1)$ 就表示第 $0$ 个位置下通道 $4\sim 7$ 的数据，以此类推。

整个系统的调度核心就是以 `pos` 为主、`group` 为次的二维坐标架构，**所有层都严格按照这个架构进行数据的接收和发送**，从而实现了全系统的无等待、无 FIFO 缓冲的流水线计算。

在计算上，我们每一层处理输出的数据称为一个 `tile`，这个 `tile` 运算到 MaxPool 的结果就是一个 $1 \times 4$ 的数据块，即一个 `pos` 下的 4 个通道的数据。我们可以从 MaxPool 输出开始，反退出前面各卷积层每一层的输出形状，从而计算其理应的输入形状，例如：
1. PWConv 为了满足能够使得 MaxPool 每个周期输出一个 $1(pos)\times 4(ch)$ 的数据，每次必须输出一个坐标为 $(\text{pos}, \text{group})$ 、形状为 $4(ch) \times 2(row) \times 2(col)$ 的 `tile`。
2. DWConv 为了满足能够使得 PWConv 每个周期输出一个 $4(ch) \times 2(row) \times 2(col)$ 的 `tile`，每次必须输出一个坐标为 $(\text{pos}, \text{group})$ 、形状为 $4(ch) \times 2(row) \times 2(col)$ 的 `tile`。
3. Conv 为了满足能够使得 DWConv 每个周期输出一个 $4(ch) \times 2(row) \times 2(col)$ 的 `tile`，每次必须输出一个坐标为 $(\text{pos}, \text{group})$ 、形状为 $4(ch) \times 4(row) \times 4(col)$ 的 `tile`。
4. 输入 Line Buffer 为了满足能够使得 Conv 每个周期输出一个 $4(ch) \times 4(row) \times 4(col)$ 的 `tile`，每次必须输出一个坐标为 $(\text{pos}, \text{group})$ 、形状为 $4(ch) \times 14(row) \times 10(col)$ 的 `tile`。

通过上面的分析我们显而易见的发现，每一层每一个周期的输出都是由二维坐标 $(\text{pos}, \text{group})$ 严格定位的。事实上，`pos` 和 `group` 就是定位每个 `tile` 的**其中两个元数据**，除此之外，还有三个元数据，这三个元数据的含义见下一节。

### 2.2 定位核心: 五大元数据

除了我们之前提到的元数据 `pos` 和 `group` 以外，还有三个元数据，分别是 `valid`、`last` 和 `fire`。它们的含义分别是：
- `valid`: 当前周期输出的 `tile` 是否**有效**。是否是真实发射进入流水线的 token 的计算结果，抑或是由于流水线未满载而产生的无效占位。
- `last`: 当前周期输出的 `tile` 是否是当前图像的**最后一个** `tile`。当 `last` 为高时，表示当前图像的所有 `tile` 已经全部输出完毕，下一周期将会开始处理下一张图像。
- `fire`: 用于不同层间通信的**启动信号**。它置高时告诉当前层开始启动计算（例如发送 SRAM 地址信号），从而保证到来的第一个 `tile` 能够立即被处理，而不用延迟一个周期等待 SRAM 读出数据。

这五个元数据十分重要，它们不仅提供了各层的运算启动/停止时机(`fire`/`valid`/`last`)，还为 testbench 调试提供了 hook(`pos`/`group`)，更重要的是——它们共同构成了整个系统的**流协议**，所有层都必须**严格遵守这个协议**进行数据的接收和发送，从而实现了全系统的**无等待、无 FIFO 缓冲**的流水线计算。

### 2.3 吞吐核心: 输入 Ping-Pong 缓存

在 CNN 的 Conv 层调度核心 `conv_core` （同时也是连接整个系统的输入与发射 token 的调度核心）发射完当前图的72个 token 后，理论上下一个周期就可以开始发送下一张图的第一个 token 了。因此为了避免两张图发射进入流水线的 SRAM 写延迟，我们在 Conv 的输入 Line Buffer 端设计了**双帧缓存（Ping-Pong Buffer）**，当一张图的 token 正在被处理时（我们记作**消费流**），下一张图的 token 可以同时被装载到另一个 `SRAM` bank 以及 `Reg` cache 中（我们记作**写入流**），因此当本张图计算完毕后，可以立刻从另一组 `SRAM + Reg` 中获取数据，从而实现两张图之间的无缝衔接，真正达到每 72 个周期输出一张图的结果。

但是在实际架构中，后续每一层包括 `DWConv`, `PWConv`, `Post_Process` 在当前输入图计算完毕之后都会存在 busy 与 done 状态的交接切换，同时也会涉及到内部计数寄存器的清理/复位，因此必须等这些层完全处于稳定状态后，`Conv` 层才能继续发送下一张图的 token, 否则会由于 `fire` 启动信号被遮蔽，导致状态错乱。故当前架构的第二次张图 token 发送时机暂定为**后续 `DWConv` 层处于空闲状态以及 `PWConv` 已经进入安全尾段（原因暂待分析）**。 

因此当前版本的双帧缓存并未实现 **72 周期一张图**的极限吞吐率，当前架构在流水稳定后的平均计算一张图需要消耗 94 个周期，依然满足 1000k FPS 的性能指标，但后续版需要完善双帧缓存机制，真正释放系统的吞吐能力。

## III. 架构痛点分析与改进方向

### 3.3 流水线吞吐率未达极限

正如在 2.3 节提到的，`DWConv` 及后续各层的状态切换与复位步骤导致 `Conv` 在计算完一张图后无法立刻发送下一张图的 token，从而导致两张图之间存在大约 20 周期的空闲时间，平均每张图的计算周期从理论上的 72 周期增加到了 94 周期，虽然依然满足了 1000k FPS 的性能指标，但距离极限吞吐率还有提升空间。

### 3.2 帧级特征累加池缺少多缓冲寄存
与输入层相同的问题同样出现在系统的末端，即 FC 的 `post_process_fc_frame_accum` 中。
该模块当前将所有 72 个 token 的归约全部放置在单套累加器（`accum_cls0`、`accum_cls1`）内计算，这就要求**前一图累加完成并进入后方** Sigmoid 与输出端口后，**才能接收并开始响应下一图像的首个 token 的清零准备操作**。在多图的高负载状况下发生流水线停滞。
**建议修正**：可利用**一组缓冲对**累加目标打底寄存切换。当前图算完即抛给后方挂起生效，让加法寄存器瞬间无延时清空迎接下一张。

## IV. 总结
SonicBolt 作为一个面向语音检测的 CNN 硬件加速器系统，采用了高度定制化的流式执行架构，通过 `pos-group` 的二维坐标架构和五大元数据的流协议，实现了全系统的无等待、无 FIFO 缓冲的流水线计算。当前版本已经实现了 Conv、DWConv、PWConv 和 Post Process 四个核心子系统，并且在处理单张 Feature Map 时在功能和性能上达到了预期目标。下一步将加入双帧缓存机制，从而**真正释放系统的吞吐能力**，向极限性能指标靠拢。
