### 1. 命名规范（Naming Conventions）
#### 规则1.1 单个文件仅包含一个设计单元（design unit）
- 规则要求：单个文件中不得包含超过1个设计单元。一个设计单元内的所有内容，必须完整包含在一对`module/endmodule`（模块/模块结束关键字）结构中。
- 制定原因：简化设计修改与维护流程。

#### 规则1.2 命名的首字符要求
- 规则要求：所有命名必须以**字母**开头，禁止以数字或下划线开头。
- 制定原因：以数字或下划线开头的命名，可能与EDA工具产生兼容性冲突。

#### 规则1.3 所有命名必须大小写无关唯一
- 规则要求：禁止通过大小写来区分单元（cell）名或信号名。
- 制定原因：部分EDA工具无法区分大小写差异；该规范可简化Verilog（大小写敏感）与VHDL（大小写不敏感）之间的设计迁移。

#### 规则1.4 常量、parameter（参数）、块标签使用全大写
- 规则要求：必须对parameter、常量名使用统一的全大写拼写。以下所有对象的字母必须全大写：常量（constant）、parameter（参数）、块标签（block label）。
- 制定原因：提供统一的识别机制，快速区分仿真过程中数值不会发生变化的对象。

#### 规则1.5 信号、结构、实例标签使用全小写
- 规则要求：必须对信号（signal）、代码结构（construct）、实例标签（instance label）使用统一的全小写拼写。
- 制定原因：区分仿真过程中会发生数值变化的信号/结构，与固定不变的常量/参数；同时在不同设计间保持统一的代码风格。

#### 规则1.6 信号与变量命名必须具备含义
- 规则要求：全小写的命名中，必须体现变量/信号的用途。
- 制定原因：通过命名即可理解设计意图。
- 正确示例：`data_bus`、`set_priority`

#### 规则1.7 多单词命名使用下划线分隔
- 规则要求：由多个单词组成的命名，必须使用下划线分隔全小写的单词。
- 制定原因：提升代码可读性。
- 正确示例：`ram_addr`

#### 规则1.8 低有效信号命名使用`_b`后缀
- 规则要求：低电平有效（active low）的信号，必须使用`_b`作为后缀。
- 制定原因：通过命名即可明确信号极性，提升设计可读性。
- 正确示例：`enable_data_b`、`reset_b`

#### 规则1.9 时钟信号命名使用`_clk`后缀
- 规则要求：用于时钟驱动的信号，若名称中未包含`clock`或`clk`，必须使用`_clk`作为后缀。
- 制定原因：通过命名即可明确时钟信号，提升设计可读性。
- 正确示例：`fifo_transmit_clk`

#### 规则1.10 状态机信号命名使用`_next`后缀
- 规则要求：建议FSM（有限状态机，Finite State Machine）的次态信号，使用`_next`作为后缀。
- 制定原因：通过命名即可明确状态机相关信号，提升设计可读性。
- 正确示例：`transmit_next`

#### 规则1.11 测试模式信号命名使用`_test`后缀
- 规则要求：建议测试模式相关信号，使用`_test`作为后缀。
- 制定原因：通过命名即可明确测试相关信号，提升设计可读性。
- 正确示例：`parallel_clk_test`

#### 规则1.12 整个层级中保持命名一致性
- 规则要求：建议在整个IP核的层级结构中，信号或设计单元的名称保持一致；多实例相关的命名，建议使用数字索引区分。
- 制定原因：提升代码可读性，避免歧义，防止综合过程中插入不必要的缓冲器（buffer）。

#### 规则1.14 Verilog命名与文档命名保持一致
- 规则要求：建议设计文档中引用的Verilog RTL内的所有信号、模块，与文档中的命名完全一致。
- 制定原因：简化HDL模型的理解与核对。

### 2. 注释规范（Comments）
#### 规则2.1 每个文件必须包含文件头
- 规则要求：每个文件必须包含文件头，所有字段必须填写，无相关内容需标注N/A。
- 制定原因：提供标准化的设计相关信息说明。

#### 规则2.2 文件头必须包含设计单元类型
- 规则要求：文件头必须说明文件中包含的最高层级设计结构类型。
- 制定原因：可快速明确文件的核心内容。
- 示例类型：`module`、`macromodule`（宏模块）

#### 规则2.3 文件头必须包含联系方式信息
- 规则要求：每个文件的文件头，必须包含所属部门、作者、作者邮箱地址。
- 制定原因：便于针对设计内容进行相关咨询。

#### 规则2.4 文件头必须包含发布历史
- 规则要求：文件头中仅需记录纳入版本库的IP修改发布历史，本地修改历史无需写入。
- 制定原因：用于跟踪设计的版本迭代记录。

#### 规则2.5 文件头必须包含用途说明章节
- 规则要求：文件头必须包含用途章节，描述模块的功能。用途说明需描述该单元提供的功能，而非实现方式。
- 制定原因：帮助快速理解模块的核心功能。

#### 规则2.6 文件头必须包含参数描述
- 规则要求：文件头必须说明设计中使用的所有parameter（参数），并标注默认值。
- 制定原因：帮助快速理解HDL代码的参数配置。

#### 文件头标准示例
```verilog
//+FHDR-----------------------------------------------------------------------
// Copyright (c) 2020, NivID.
// Motorola Confidential Proprietary
//----------------------------------------------------------------------------
// FILE NAME      : 【文件名】
// TYPE           : 【文件类型，可填module、macromodule】
// DEPARTMENT     : 【所属部门】
// AUTHOR         : 【作者】
// AUTHOR’S EMAIL : 【作者邮箱】
//----------------------------------------------------------------------------
// Release history
// VERSION  Date         AUTHOR    DESCRIPTION
// 1.0      6 Oct 2020   name      【版本描述】
//----------------------------------------------------------------------------
// KEYWORDS : 【通用文件检索关键词，无则留空】
//----------------------------------------------------------------------------
// PURPOSE : 【模块功能的简短描述】
//----------------------------------------------------------------------------
// PARAMETERS
// PARAM NAME      RANGE    : DESCRIPTION           : DEFAULT : UNITS
// e.g.DATA_WIDTH  [32,16]  : width of the data    : 32      :
//----------------------------------------------------------------------------
// REUSE ISSUES
// Reset Strategy      : 【复位策略】
// Clock Domains       : 【时钟域】
// Critical Timing     : 【关键时序路径】
// Test Features       : 【测试相关特性】
// Asynchronous I/F    : 【异步接口】
// Scan Methodology    : 【扫描链实现方式】
// Instantiations      : 【内部实例化的模块】
// -FHDR-----------------------------------------------------------------------
```

### 3. 代码风格（Code Style）
#### 规则3.1 使用2-4个空格进行代码缩进
- 规则要求：代码对齐必须使用固定的2-4个空格进行缩进，禁止使用制表符（Tab）。可使用空格和空行提升代码可读性。
- 制定原因：提升代码可读性。

#### 规则3.2 每行仅写一条Verilog语句
- 规则要求：单行内不得包含多条语句，禁止将多个以分号分隔的Verilog语句写在同一行。
- 制定原因：提升代码可读性，便于设计工具解析代码。

#### 规则3.3 使用单行注释
- 规则要求：必须使用单行注释`//`，禁止使用多行注释`/*...*/`。
- 制定原因：提升代码可读性与代码解析兼容性。

#### 规则3.4 明确标注端口类型，单行仅声明一个端口
- 规则要求：必须明确声明每个端口的类型，单行仅声明一个端口。
- 制定原因：提升代码可读性与可理解性，便于脚本解析代码。
- 正确示例：
```verilog
input  a;
input  b;
```
- 错误示例：
```verilog
input a, b;
```

#### 规则3.6 端口声明顺序与端口列表保持一致
- 规则要求：建议端口声明的顺序，与模块端口列表中的顺序完全一致。
- 制定原因：提升代码可读性。

#### 规则3.7 为每个端口添加注释说明
- 规则要求：建议每个端口声明后，添加描述性注释，优先写在同一行。
- 制定原因：提升代码可读性。

#### 规则3.8 时钟生成电路独立分块
- 规则要求：时钟生成电路必须独立成一个单独的模块，放在IP核的顶层，或与对应时钟域的模块处于同一逻辑层级。
- 制定原因：简化测试策略的生成，将编码规范的例外情况限制在小模块内，同时提升代码在不同时钟方案下的可移植性。

#### 规则3.9 所有模块输出必须加寄存器打拍
- 规则要求：建议所有模块的输出信号都经过寄存器（register）打拍输出。
- 制定原因：简化与其他模块的时序接口设计，以及综合流程。
- 例外情况：不可综合的代码不适用本规则。

#### 规则3.10 不同时钟域独立分块
- 规则要求：建议将不同的时钟域，拆分到独立的模块中；两个时钟域之间的同步逻辑，也建议拆分到独立的模块中。
- 制定原因：简化综合流程，避免对单一时钟域进行过度约束。

#### 规则3.11 异步逻辑与同步逻辑独立分块
- 规则要求：建议将异步逻辑（asynchronous logic）与同步逻辑（synchronous logic）拆分隔离。
- 制定原因：避免综合出现问题，简化时序约束与脚本编写。
- 例外情况：不可综合的代码不适用本规则。

#### 规则3.12 状态机独立分块
- 规则要求：建议将FSM（有限状态机）的代码独立写在单独的块/模块中。
- 制定原因：避免综合出现问题，简化时序约束与脚本编写。

#### 规则3.13 禁止在同一结构内混合结构型与行为型RTL代码
- 规则要求：建议通过模块划分，将结构型代码与行为型RTL代码完全隔离；每个模块必须是纯结构型，或纯行为型RTL。
  注：结构型代码指仅包含电路连接信息的代码。
- 制定原因：混合编码可能导致综合出现问题与限制。

#### 规则3.14 禁止将信号赋值为x
- 规则要求：禁止将信号赋值为x，必须为所有信号赋予合法的已知数值。
- 制定原因：避免x态在电路中传播，导致仿真与综合结果不一致。

#### 规则3.15 禁止在函数中推断出锁存器
- 规则要求：禁止在任何函数调用中推断出锁存器（latch）。
- 制定原因：函数必须综合为纯组合逻辑电路。

#### 规则3.16 存储单元优先使用同步复位
- 规则要求：建议所有场景下优先使用同步复位（synchronous reset）。
- 制定原因：简化扫描链（scan chain）的插入与测试流程。

#### 规则3.17 always块敏感列表必须完整
- 规则要求：所有推断组合逻辑或锁存器的always块，必须包含敏感列表，且敏感列表必须包含所有输入信号。
- 制定原因：无论敏感列表如何编写，综合工具都会生成依赖所有读取值的电路结构，不完整的敏感列表会导致行为级仿真与门级仿真出现潜在的不匹配。

#### 规则3.18 单个always块仅对应一个时钟
- 规则要求：同步时序逻辑的Verilog always块中，只能使用一个时钟。
- 制定原因：确保每个语句块仅推断出一种类型的存储单元。

#### 规则3.19 禁止使用wait语句与#延迟语句
- 规则要求：设计中禁止使用显式或隐式的wait语句，以及`#`延迟语句。
- 制定原因：RTL到门级的综合流程，通常不支持wait语句与#延迟语句。

#### 规则3.20 组合逻辑条件表达式必须完整
- 规则要求：条件表达式必须完整声明，即变量/信号在所有条件下都必须被赋值。
- 制定原因：如果组合逻辑的条件表达式不完整，综合工具会推断出存储单元（锁存器）。
- 正确示例：
```verilog
always @(signal_names) 
case (signal_names)
  3'b000,
  3'b001 : output =4'b0000; 
  3'b010 : output = 4'b1010;
  3'b011,
  3'b100,
  3'b101: output = 4'b0101;
  3'b110,
  3'b111 : output = 4'b0001;
endcase
```
- 错误示例：
```verilog
always @(signal)
begin
  if (signal ==1'h1)
    output =4'b0;
end
```

#### 规则3.21 禁止使用initial语句
- 规则要求：复位功能、信号与变量的初始化，必须显式建模实现，禁止使用initial结构。
- 制定原因：综合后的门级网表不会保留initial结构的初始化内容，会导致行为级与门级模型的仿真不匹配。
- 例外情况：允许在testbench（测试平台）中使用initial语句。

#### 规则3.22 端口连接中禁止使用表达式
- 规则要求：模块端口连接中禁止使用表达式。
- 制定原因：可能导致模块之间生成粘合逻辑（glue logic），同时降低HDL代码的可读性。
- 例外情况：允许使用总线位拼接操作。

### 4. 其他编码技巧（Other Coding techniques）
#### 规则4.1 禁止使用Verilog原语（primitive）
- 规则要求：禁止使用Verilog内置原语。
- 制定原因：避免底层原语导致的综合兼容性与可移植性问题。

#### 规则4.2 边沿敏感结构中必须使用非阻塞赋值（<=）
- 规则要求：边沿敏感的时序逻辑块中，必须使用非阻塞赋值（non-blocking assignment, <=），禁止使用阻塞赋值（blocking assignment, =）。
- 制定原因：边沿敏感的时序代码中使用阻塞赋值，会导致综合前后仿真结果不匹配。
- 正确示例：
```verilog
always @(posedge clk) begin 
  regb <= rega; 
  rega <= data; 
end
```
- 错误示例（会导致综合前后仿真不匹配）：
```verilog
always @(posedge clk) begin 
  rega = data; 
  regb = rega; 
end
```

#### 规则4.3 所有内部线网声明集中在一个区块
- 规则要求：内部wire（线网）的声明，必须统一放在模块端口I/O声明之后的模块顶部。
- 制定原因：提升代码可读性，便于快速查阅所有内部信号。

#### 规则4.4 必须显式声明所有内部线网
- 规则要求：所有内部wire必须显式声明，禁止使用隐式线网。
- 制定原因：尽管Verilog语法支持隐式线网，但显式声明可避免命名错误导致的歧义与问题。

#### 规则4.5 禁止使用casex语句
- 规则要求：所有case语句必须使用`case`或`casez`，禁止使用`casex`。
- 制定原因：casex会在综合中将X和Z态视为无关项，可能导致综合前后的仿真行为不一致。

#### 规则4.6 使用parameter进行状态编码
- 规则要求：建议使用枚举型parameter，对状态机的不同状态进行编码。
- 制定原因：便于修改状态机的实现方式，例如从独热码（1-hot）切换为格雷码（gray code）。
- 正确示例：
```verilog
parameter [1:0] // synthesis enum state_info
  RESET_STATE = 2'b00,
  TX_STATE    = 2'b01,
  RX_STATE    = 2'b10;
```

#### 规则4.7 禁止在设计顶层添加粘合逻辑
- 规则要求：建议不要在设计层级的顶层，实例化或推断门级电路。
- 制定原因：顶层逻辑无法被综合工具合并优化，会限制综合结果。

#### 规则4.8 避免使用inout类型端口
- 规则要求：建议优先使用input或output类型端口，避免使用inout（双向）类型端口。
- 制定原因：双向端口的实现可能导致信号竞争问题，同时简化综合与测试电路插入流程。

#### 规则4.9 阻塞赋值的使用规范
- 规则要求：建议组合逻辑使用阻塞赋值（blocking assignment, =）。
- 制定原因：阻塞赋值的仿真速度通常快于非阻塞赋值。
- 注意事项：为避免执行顺序导致的依赖问题，推断锁存器时需格外注意。
- 例外情况：锁存器与触发器混合设计中的锁存器，建议使用非阻塞赋值。

#### 规则4.10 case语句必须添加default分支
- 规则要求：建议所有组合逻辑的case语句，都必须添加default分支赋值。
- 制定原因：未显式声明的case选择组合，可能导致综合前后的仿真结果不匹配。
- 注意事项：使用default分支可能会推断出额外的逻辑。
- 正确示例：
```verilog
casez (sbus_sel[2:0])
  3'b100: sbus_data[31:0] = in_bus[31:0];
  3'b?1?: sbus_data[31:0] = 32'b1;
  3'b?01: sbus_data[31:0] = data_rd[31:0];
  default: sbus_data[31:0] = 32'h0;
endcase
```
