### 一、 单个并行计算单元的内部结构：加法树（Adder Tree）

在软件中，你要算一个包含 $N$ 个元素的点积（比如 11×7 的一行 7 个元素），你会写一个 `for` 循环，把它们一个个累加。
但在硬件中，为了在一拍（一个时钟周期）内算出这 7 个元素的乘累加和，我们会使用**空间展开的加法树（Adder Tree）**。

以一次并行处理 **8 个输入（补充一个0或者对齐用）** 为例，它的结构是一棵倒置的二叉树：

```text
输入特征图(INT8):  I0  I1  I2  I3  I4  I5  I6  I7
卷积核权重(INT8):  W0  W1  W2  W3  W4  W5  W6  W7
                   │   │   │   │   │   │   │   │
【Stage 1: 乘法】  X   X   X   X   X   X   X   X   <-- 8个并行的硬件乘法器(打一拍)
(INT16)            │   │   │   │   │   │   │   │
                   P0  P1  P2  P3  P4  P5  P6  P7
                    \ /     \ /     \ /     \ /
【Stage 2: 加法】    +       +       +       +     <-- 4个加法器 (打一拍)
(INT17)              │       │       │       │
                     S0_1    S0_2    S0_3    S0_4
                       \      /        \      /
【Stage 3: 加法】        +                +        <-- 2个加法器 (打一拍)
(INT18)                  │                │
                         S1_1             S1_2
                           \               /
【Stage 4: 加法】                  +               <-- 1个加法器
(INT19)                            │
                             Total_Sum (本拍总和)
                                   │
【Stage 5: 累加与偏置】  Acc_Reg <= Acc_Reg + Total_Sum (+ Bias)  <-- 累加器(INT32)
```

**设计要点：**
1. **流水线切割**：这棵树不能在一个周期内硬算到底（会导致严重的 Setup Time 违例）。必须在每一层（或每两层）插入寄存器打拍。比如数据从进入乘法器到最后累加出结果，可能需要经历 3~4 个时钟周期的**流水线延迟（Latency）**。
2. **位宽递增**：正如前面所说，8位乘8位=16位；两个16位加=17位... 硬件工程师必须精确计算每一级的位宽，防止溢出，同时也不能无脑全给 32 位（太浪费面积）。

### 二、 多个 MAC 树的协同：广播与通道并行（Channel Parallelism）

单个 MAC 树算得再快，也只能算一个卷积核的结果。在你们的第一层 `Conv1` 中，输入通道是 1，但**输出通道有 32 个（即 32 个不同的卷积核同时在看同一块特征图）**。

这就是数字 IC 架构中极其优美的**输入广播机制（Input Broadcasting）**！

#### 场景推演：
当 Line Buffer 凑齐了 11×7 的滑动窗口，准备输出数据时：

1. **共享输入特征（Input Feature Map）**：这 77 个 INT8 的输入像素，被**复制（广播）**成 32 份，同时喂给 32 棵独立的 MAC 树！（在物理连线上，就是把这根线像树枝一样分叉连到 32 个模块的输入端）。
2. **独立的权重（Weights）**：这 32 棵 MAC 树，每棵树内部寄存器里存的权重是不一样的（分别是 Filter 0 到 Filter 31 的权重）。
3. **并发输出**：经过 3~4 拍的流水线延迟后，这 32 棵 MAC 树会在**同一个时钟周期**，齐刷刷地吐出 32 个 INT32 的累加结果！
4. **数学意义**：这就意味着，你仅仅滑动了一次窗口，就彻底算完了当前空间位置 $(x, y)$ 上**所有 32 个通道的像素点**！输出特征图的长条 $(32, 1, 1)$ 在一瞬间被计算完毕。

**这种“复用输入、并行通道”的架构，极大节省了 SRAM 的读取带宽，是现代 NPU（如谷歌 TPU、苹果 NPU）最底层的逻辑。**

### 三、 全链路流水线协同：数据在工厂中的一生

为了让你看到全局，我们把之前聊过的所有模块（Line Buffer -> MAC Array -> Requantization -> Ping-Pong Buffer）串联起来，看看流水线是怎么协同的。

假设我们采用“每周期算完一整个空间像素（即 77 个乘法 × 32 通道）”的极其残暴的超高并行度架构：

*   **拍数 T=0：数据就绪**
    *   Line Buffer 的指针更新完毕，凑齐了最新的 11×7 窗口。
    *   产生信号 `window_valid = 1`。

*   **拍数 T=1：乘法级 (MAC 阵列内部)**
    *   32 个 MAC 树接收到了广播的输入数据，第一级数千个乘法器同时完成计算。
    *   此时，Line Buffer **没有停下**！它可能已经移位，准备好了下一个相邻窗口的数据（下一个 `window_valid = 1` 紧跟其后）。

*   **拍数 T=3：累加完毕 (MAC 阵列输出)**
    *   经过几级加法树，32 个 MAC 树算出了完整的 INT32 结果，加上了各自的 Bias（偏置）。
    *   产生信号 `mac_out_valid = 1`。这 32 个 INT32 数据像包裹一样传递给下一站。

*   **拍数 T=4：重量化与激活 (Requantization & ReLU)**
    *   我们之前讨论过的 `RescaleReLu` 模块接收到 `mac_out_valid`。
    *   它将 32 个庞大的 INT32 乘以定点数 $M_0$ 并右移 $N$ 位，如果小于 0 则置 0（ReLU），最后截断回 32 个精巧的 INT8 数据。

*   **拍数 T=5：写入下游 (Ping-Pong Buffer 或下一个 Line Buffer)**
    *   这 32 个 INT8 数据（正好是输出特征图的一个完整像素点的 32 个通道），带着最终的 `final_valid = 1` 信号，被写入 Bank A 的对应地址中。

**发现了吗？这就像一条完美的汽车装配流水线！**
虽然一辆汽车（一个最终的输出像素）从头走到尾需要 5 拍的时间（Latency = 5），但是流水线上每个工位都在同时忙碌。
从 T=5 开始，**每一个时钟周期，系统的最末端都会齐刷刷地掉出 32 个处理完的 INT8 像素！** 吞吐量达到了恐怖的 1 Cycle / 像素。

### 💡 针对你们“高性能（1000K FPS）”场景的算力估算与建议

我们来算一笔硬核的架构账。你要说服老师你们的设计是“高性能”，必须有数据支撑。

1. **时间约束**：
   假设综合后的时钟频率是 $150 \text{MHz}$。
   要求 $1000\text{K}$ FPS，即每秒处理 1000,000 帧。
   平均每帧处理时间 = $150,000,000 / 1000,000 = \textbf{150 个时钟周期}$。
   这意味着，你们必须在 150 拍内，算完第一层卷积！

2. **Conv1 工作量**：
   输出特征图是 `(32, 20, 4)`，即空间上有 $20 \times 4 = 80$ 个像素。
   如果我们采用上面说的**“通道全展开（并行32），窗口全展开（并行77）”**的架构，算完一个空间像素需要 1 拍（不含初始流水线延迟）。
   算完 80 个像素只需要 $\mathbf{80 \text{ 拍}}$！
   80 拍 < 150 拍，**完美满足高性能要求，甚至还有余量！**

3. **硬件代价（Trade-off）**：
   这种方案需要 $32 \text{ (通道)} \times 77 \text{ (窗口)} = \mathbf{2464 \text{ 个乘法器}}$！
   在 0.18um 工艺下，2464 个 8-bit 乘法器面积会比较大，但这完全符合你们选择的“场景二：高性能应用场景”的核心评价指标（$\text{Speed}/\text{Area}$），因为你的 Speed 极快！

4. **优化备选（折中方案）**：
   如果觉得 2464 个乘法器太多，EDA 跑不出来，可以只展开**一行（7个乘法器）**。
   每个 MAC 树有 7 个乘法器。计算 1 个像素需要分 11 次（11行）累加，即 11 拍算完 1 个像素的所有 32 通道。
   总周期数 = $80 \times 11 = \mathbf{880 \text{ 拍}}$。
   *注意：此时 880 拍 > 150 拍了！如果不提高时钟频率（比如拉到 $1\text{GHz}$，这对初学者几乎不可能），就无法满足 1000K FPS。*

**团队战术建议**：
既然选了高性能，就**暴力美学到底**！建议你们在设计 Conv1 时，就采用**通道并行 32，窗口局部或全部展开**的架构。通过极其宽广的数据通路（Datapath），榨干硅片的每一寸面积换取吞吐量。把上面的算力推导写进你们的设计文档里，这就叫**“顶层架构驱动的 RTL 设计”**！
